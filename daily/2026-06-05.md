## Auditor ↔ Pact 接缝说明 v0

Auditor 不替代 CAW，也不重写 CAW 的 policy 执行层。CAW 负责 **enforce**：签名层、allowlist、额度、频率、审批、撤销、链上执行。Auditor 负责 **explain + preflight**：解释这笔操作为什么服务用户意图、收款地址从哪里来、价格是否合理、是否存在注入或字段偷换。

接缝应该放在 **Pact 提交前 / 用户审批前**：

```text
Agent 生成 payment draft
  -> Auditor 生成 risk_summary
  -> 计算 summary_hash
  -> 用 risk_summary 的关键字段生成 / 校验 Pact policy
  -> 用户同时看 risk_summary + Pact 审批
  -> 用户确认后记录 user_confirmation_id
  -> CAW 执行前校验 summary_hash / policy / tx draft 是否仍一致
```

关键原则：**用户批准的对象必须和 CAW 执行的对象同一份语义对象**。如果 `recipient_address / amount / token / chain_id / policy / summary_hash` 任一关键字段变化，就不能 refresh 后继续执行，必须重新生成 risk summary 并重新进 human gate。

今天这版 schema 先解决 transaction substitution 的最小绑定问题：

- `summary_id`：Auditor 摘要身份。
- `summary_hash`：摘要 canonical JSON 的 hash，防止摘要内容被改。
- `pact_policy`：CAW 能执行的硬边界。
- `payment`：最后要执行的链上语义字段。
- `user_confirmation_id`：用户对这份摘要的单次批准。
- `pact_id`：CAW 接收并进入审批/执行的对象。

这不是为了把 CAW 变复杂，而是为了避免 demo 里最危险的漏洞：**用户看到的是安全计划 A，实际被 Agent 送去 CAW 的是交易 B**。

### 今天最大的认知

昨天的证据证明了 CAW 是一条能执行的轨道；今天真正想清楚的是，Auditor 的价值不是再造一条轨道，而是保证**进入轨道的对象没有被语义污染或字段偷换**。CAW 可以判断"这笔交易是否在 policy 内"，但它不知道这个 vendor 是否真的服务用户意图、地址是否来自可信来源、risk summary 和 Pact policy 是否描述的是同一件事。

所以 Auditor/Pact 接缝的核心不是"多写一个摘要"，而是把摘要变成可绑定对象：`summary_hash + payment fields + pact_policy + user_confirmation_id`。没有这层，human gate 可能变成橡皮图章；有了这层，用户批准才真正指向最后执行的那笔 CAW 操作。
